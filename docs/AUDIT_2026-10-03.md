5. **No secret was found** in the working tree or in any of the 130 commits. (Part 11.)
6. **All CI jobs on `main` pass** after the audit fix (PR #56) and the `e2e/node_modules` cleanup (PR #57). (Part 10.)

## Part 3. Sign-in: `web/auth.js`, `web/account.js` and the Supabase migrations

**Order of screens** (`web/auth.js:28-40`, function `gateView`): sign in → set up the authenticator app (MFA) → enter the 6-digit code (needs assurance level `aal2`) → wait for the profile → "rejected" or "pending" → acknowledge the intended-use statement → the app.

**Behaviour** (all VERIFIED by reading):
- Supabase JavaScript library, vendored (`web/vendor/supabase.min.js`); `flowType: "implicit"`, session kept in the browser's `localStorage` under `diacausal-auth` (`web/auth.js:75`).
- Passwords: at least 12, at most 72 characters; a list of common passwords is refused (`web/auth.js:24-25`, `:43-55`).
- Idle sign-out after 15 minutes (`web/auth.js:23`, `:191-192`).
- Sign-up collects name, email, password and a **self-chosen role** (`clinician`, `student` or `examiner`). The role is not verified (`web/auth.js:123-130`; `supabase/migrations/20260926000000_accounts.sql:11`).
- If `web/config.json` has no Supabase settings (the committed file says `"accounts": "off"`), sign-in is off and every tab is open; a "demo" banner shows (`web/app.js:464-471`; `web/config.json`). The deployed copy gets real settings from `scripts/web_config.py`, which refuses to write into `web/`.
- The browser also caches the signed-in person's profile (name, email, role, approval) in `localStorage` (`web/auth.js:82-83`).

**Database** (three migrations in `supabase/migrations/`):
- `20260926000000_accounts.sql`: table `public.profiles` (id, full name, email, role, `approved`, `rejected`, `is_admin`, timestamps). Row-level security is on. A person can read only their own row; an admin who has passed MFA reads all (lines 41-45). Nobody can insert, update or delete directly (lines 110-112). A trigger creates the profile at sign-up with `approved = false` (lines 47-70). `approve_user()` needs an admin with MFA (lines 72-91). `acknowledge_intended_use()` stamps the acknowledgement (lines 93-100). No patient values, questions or results are stored (comment at line 5).
- `20260926000100_private_is_admin.sql`: moves the admin check into a private schema (`private.is_admin`) and revokes it from the public and anonymous roles.
- `20260926000200_approved_by_set_null.sql`: lets the approver's account be deleted without deleting the approved person.

**Which tabs are gated.** Try it and Evidence are gated; Results, Learn and About are open. **The gate is enforced in the browser only.** `model.json` (110 KB), `evidence.json` (1.27 MB) and `results.json` (21 KB) returned HTTP 200 to a plain request with no sign-in (VERIFIED, live site), and `web/sw.js:6-30` caches them on the device. The only server-side check is in the Gemini Edge Function (Part 4). Because the data files hold only the synthetic-cohort model, public guideline text and results, this is a convenience gate, not a confidentiality control; the UI should not claim more. Whether that matches the team's intent is a decision for the team.

**How the DR-learner's final stage is fitted** (`diacausal_engine/estimators.py:136-253`, VERIFIED by reading):
1. Per-fold outcome models: one `HistGradientBoostingRegressor` per option, trained on the other folds' patients who got that option and used on this fold (cross-fitting; `:139-158`).
2. A propensity model (`propensity.py`, floor 0.05 from `data/params.yaml:215`).
3. The doubly robust score for each patient and option: `phi = mu + 1{T=a} (Y − mu) / e` (`aipw_scores`, `:163-172`).
4. Pseudo-outcomes: the score for each option plus each pairwise difference, six columns (`pseudo_outcomes`, `:188-191`).
5. **Final stage: ordinary least squares of each pseudo-outcome on a standardised constant-plus-covariates basis** (`DRLearner.fit`, `:204-215`), with **HC3 robust covariance** (leverage-adjusted, `:212-214`).
6. The estimate is `x'beta`; the 95% interval is `x'beta ± 1.96 sqrt(x'Vx)` (`predict`, `:221-231`).

Two consequences worth knowing for P11 and P25: the final stage is **linear**, so a SHAP explanation of it is exact and simple (each covariate's contribution is its coefficient times how far the patient is from the average), and the interval covers the fitted linear model's uncertainty, not the uncertainty of the earlier boosted models, and not the error if the true effect is not linear. An option whose interval is wider than `max_interval_width` (1.5 percentage points, `data/params.yaml:232`) abstains.
